Both arms make the teacher prefill nearly the same number of new tokens (~660k), so their base-model prefill work is comparable. Candidate projection, response serialization and request scheduling are not identical: the legacy arm materializes one large candidate matrix per sample, while the blocked arm issues many bounded replies and reuses the growing prefix through the radix cache (97.5% hit). Under the configured eight-request in-flight bound, that trade reduces the observed scoring tail and step time.

2 · Long responses: legacy exceeds the configured step deadline

With the default chat template the student writes thinking traces up to 16k tokens. The legacy path scores each sample with one request whose reply materializes positions × response-wide candidate-union log-probs. Why the asymmetry: candidate-response mechanics

For a response of T positions with top-k K:

  • legacy: one request, candidate union U ≈ unique(T×K) ids, reply carries T × U log-probs — quadratic-ish in T. At T≈1.5k this is tolerable; at T≈9k+ a single reply is hundreds of millions of values.
  • blocked: T/B requests; block b carries the union of its own B rows only (U_b ≤ B×K), so candidate-response cells are bounded by T×B×K for fixed B. Consecutive blocks share the sequence prefix, so the teacher's radix cache eliminates most repeated model prefill (~98% hit measured).

This does not make the entire HTTP exchange linear. Every block still sends the prompt plus a growing response prefix; total request input IDs are roughly (T/B)×P + T²/(2B). Prefix caching removes most repeated GPU prefill, not request-body transfer or scheduler overhead. The block size therefore trades candidate-response size against request count and repeated prefix transfer.

For a fixed scorer snapshot, each position retains the same candidates and objective values; unit parity tests cover all three weight modes. The cluster runs establish end-to-end behavior and timing, not bit-exact score parity.

4 · Teacher candidate set (only-teacher)

The runs above cover only-student: the fixed teacher scores position-blocked student candidates. The only-teacher pair uses teacher-native candidates and asks the student rollout router to score them:

OPD_TOP_K_STRATEGY=only-teacher OPD_TOP_K_SCORING_BLOCK_SIZE=0 \
  bash examples/on_policy_distillation/run-qwen3-8B-opd.sh

OPD_TOP_K_STRATEGY=only-teacher OPD_TOP_K_SCORING_BLOCK_SIZE=32 \
  bash examples/on_policy_distillation/run-qwen3-8B-opd.sh

All four cells ran the synchronous official example, so student weights are stable within each rollout round. Fully asynchronous only-teacher additionally needs a student weight-version consistency contract across block requests.

4a · Engine-layer precondition: arbitrary-ID scoring on busy engines

The first attempt crashed all four cells identically — both arms, both workloads — about 30 seconds after generation started: the first rescore request that reached a rollout engine killed its scheduler process with AttributeError: 'list' object has no attribute 'tolist' (batch_result_processor.py), and the router returned 503 once no workers remained. LogitsProcessorOutput.next_token_token_ids_logprobs_val is declared to hold host lists as well as tensors (delayed-copy prefill-only requests), and the serving stack's D2H relay already guards each entry with torch.is_tensor; two normalization sites called v.tolist() unconditionally. A dedicated scoring server never hits that path — it has no concurrent decode traffic — which is why the only-student cells were unaffected. The guard fix plus regression tests were applied to the serving stack before collecting the results below. This failure layer is independent of block size: it gates the strategy itself, not the transport.

With the engine bug fixed, the long-response failure cleanly isolates the transport problem: rollout engines serve rescore requests between decode batches, the response-wide union's demand outpaces that service rate, and the queue consumes whole deadlines before requests are even issued. The blocked arm's bounded requests interleave with decode without building a backlog.
